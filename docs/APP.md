# ess-share / ess-share-ui / ess-view 使用说明（v0.7 原型）

屏幕共享的三个可执行程序：`ess-share-ui`（图形分享端）、`ess-share`（命令行分享端）
采集并发送，`ess-view`（原生观看端）接收并显示；观看方也可以只用浏览器（见下）。

## 依赖

- LiveKit 服务器（官方二进制，**不进仓库**；获取与校验见 README「LiveKit 服务端怎么带」。
  本机放好后设 `LIVEKIT_SERVER=<路径>`；不设则找程序目录同级，再找仓库兄弟目录 `livekit-probe/`
- 构建：`cargo build --release -p ess-app`（产物在 `target/release/`）

## 快速开始（本机）

**图形分享端一步就绪**：跑 `target/release/ess-share-ui`，点「开始共享」。服务器那一格是回环地址
（默认即是）时，它自己拉起 `livekit-server`、在进程内起好观看页、探测本机局域网地址，
界面上给出可点的观看链接；退出时收掉自己起的那个服务端。命令行等价物：

```bash
target/release/ess-share --host-viewer      # 服务端 + 观看页 + 会话，一条命令
target/release/ess-view                     # 原生观看端（别的设备用浏览器，免安装）
```

要单独看某一步的日志时再手工分开：

```bash
# 终端 1：服务端（dev 模式，自带 devkey/secret，只绑 127.0.0.1）
"$LIVEKIT_SERVER" --dev

# 终端 2：观看端（窗口显示）
target/release/ess-view

# 终端 3：共享端（采集主屏）
target/release/ess-share
```

默认参数：`--url ws://127.0.0.1:7880 --room demo --identity share/view --fps 30 --key devkey --secret secret`。
地址相关：`LIVEKIT_SERVER`（服务端二进制位置）、`ESS_ADVERTISE_IP`（钉死对外宣告的网卡地址）。

## 图形分享端（Tauri）

```bash
cargo build -p ess-share-ui --release --features custom-protocol
target/release/ess-share-ui
```

- 窗口内填写服务器/房间/身份/帧率（**上限 60**），勾选「合成屏」可不开采集做演示；
  「高级：画质」里可选视频清晰度上限（自动/720p/1080p）与视频码率（自动/2/4/6/10 Mbps）——
  画质与流畅度的取舍按产品要求交给用户选，代码里只定默认档；
  「高级：密钥」里是 API Key/Secret（dev 模式默认 devkey/secret）。
  「高级：密钥」里是 API Key/Secret（dev 模式默认 devkey/secret）。
- **帧率是承诺**：采集按设定的绝对时刻排程，处理不过来时降画质而不是降帧。
  决策器按「每 8 像素采样的变化比例 ≥ 25%」判定大面积运动，命中即切到
  **视频平面**：会话开始就发布一条屏幕共享视频轨（默认 H264 1280×720@fps、
  4 Mbps、优先保帧率），运动期间整帧转 I420 喂给编码器；静止 10 帧后切回无损
  图块。没有视频轨时（`ESS_VIDEO=0`）退回整帧 800×450 JPEG（4:4:4）。
- **平面交接契约**（对标远控软件的关键，两条都是硬约束）：
  1. 退出运动时**先发修复、后发 `VideoMode{off}`**。可靠通道有序，观看端因此把
     "收到 off" 当作"画布已经正确"的信号——顺序反了就会看到画面退回运动前。
  2. 视频平面期间**不发有损帧**，观看端画布始终等于最后一次无损画面；退出只需
     补真正的差集（实测一次退出修复 216 块，而整帧是 1.2–1.5 MB），画面绕回原样
     时甚至一个像素都不用发。观看端进入平面时还要等 `<video>` 真的交出一帧新画面
     才接管显示（`requestVideoFrameCallback`），避免闪出上一次运动的旧帧。
- 开关（环境变量，CLI 与 UI 通用）：`ESS_VIDEO=0` 关掉视频轨、
  `ESS_VIDEO_CODEC=h264|vp8|vp9|av1`（默认 h264）、`ESS_VIDEO_SCREENCAST=0` 关闭
  屏幕共享码控、`ESS_VIDEO_MAX_W`/`ESS_VIDEO_MAX_H` 改分辨率上限、
  `ESS_VIDEO_BITRATE` 改码率（不设则按 帧率x像素 自动定档）、`ESS_MOTION*` 见 `ess-core::pipeline`、
  `ESS_RECONNECT_GRACE_S` 改"永久断线多久判定会话结束"（默认 30 s）、
  `ESS_CAPTURE=gdi|dxgi` 强制采集通路（不指定时按帧率自动选，见上）、`ESS_PERF=1`
  打印每秒指标（含 `REPAIR exits/tiles`）、`ESS_DEMO_FLASH=1` 让合成屏每 2 s 输出
  一次墙钟对齐白闪（延迟测量用）。
- **码率阶梯**（`scripts/bitrate-ladder.sh`，最坏内容：全屏逐帧随机色重绘，1080p60，
  H264 + screencast；观看端 `dims` 就是编码器实际交出的分辨率）：

  | 目标码率 | 实际编码分辨率 | 发送端 | 浏览器呈现 |
  |---|---|---|---|
  | 2 Mbps | **降到 1280x720** | 61 fps | 38 fps |
  | 4 Mbps | 1920x1080 | 60 fps | 53 fps |
  | 6 Mbps | 1920x1080 | 61 fps | 60 fps（丢帧 12%） |
  | 10 Mbps | 1920x1080 | 60 fps | 60 fps（丢帧 5%） |

  两件事被这一组数据证实：`degradation_preference = MaintainFramerate` 确实是
  **降分辨率而不是降帧**（发送端每一档都守住 60–61 fps）；4 Mbps 撑不住 1080p60。
  默认码率因此改成按 `像素 x 帧率 x 0.09 bpp` 自动定档，夹在 1.5–12 Mbps
  （1080p30 → 5.6 Mbps，1080p60 → 11.2 Mbps；4K 撞上限后由编码器自己降分辨率）。

- **帧率档位扫描与采集通路上限**（`scripts/video-tier-sweep.sh`，真机 1920×1080 采集 +
  H264 视频平面，`ESS_MOTION_HOLD=4000` 把平面钉在视频侧）。发送端每帧管线成本：
  720p 轨 7 ms，1080p 轨 13 ms。`--fps 60` 只跑到 32 fps 的锅**不在采集 API**，
  而在被测内容本身只有约 2 Hz 在变（白闪窗口 2 s 一次）——GDI 抓屏会等合成。
  换成持续重绘的全屏窗口（`target/video-demo/fast.ps1`）再测同一设置：

  | 采集通路 | 设定 60 fps 实际产出 | 每帧成本 |
  |---|---|---|
  | GDI BitBlt（默认） | 53–56 fps | 8 ms |
  | DXGI 桌面复制（`ESS_CAPTURE=dxgi`） | **60–61 fps** | 10 ms（其中拷贝+映射 6 ms） |

  同一台机器（AMD RX 6650 XT，显示器 165 Hz）的基准，
  `cargo test -p ess-capture --release -- --ignored --nocapture`：

  ```
  静止桌面：纯 BitBlt 31.5 fps；frame() 全链路 31.5 fps（等合成，不是拷贝的锅）
  持续重绘：BitBlt 82 fps；frame() 82 fps (12.2 ms/帧)
  持续重绘：Duplication 新帧 164.9/s（= 刷新率），每帧拷贝+映射 6.06 ms
  ```

  结论：≤50 fps 的档位 GDI 够用；要 60 fps 必须用桌面复制，GDI 满载只能给到 49–55。
  GDI 在 40 与 50 fps 档是精确达标的（40/50、51/50），设 60 只能给到 49–55。
  会话因此**按设定的帧率自动选路**：`fps > 50` 用桌面复制，
  否则用 GDI；显式指定 `ESS_CAPTURE=gdi|dxgi` 可以覆盖，dxgi 起不来（无 GPU 会话、
  输出被拔、`DuplicateOutput` 失败）自动回落 GDI 并在日志里说明原因。
  两条通路都要有鼠标指针：GDI 用 `DrawIconEx`，桌面复制自己合成 `GetFramePointerShape`
  （`dxgi::composite_pointer`）。踩过的坑：单色形状的 `Height` 有时报整个缓冲的行数
  （两个平面）有时报可见高度，本机同一支箭头先后报过 32 和 64——必须按缓冲区实际
  行数判，否则指针直接不画。彩色（COLOR）是 32bpp **预乘** alpha，`dst = src + dst*(1-a)`。
  验证：`cargo test -p ess-capture -- --ignored` 的 `duplication_paints_pointer` 把光标
  停到屏幕中心 → 确认合成位置与形状类型 → 再把光标移开，断言原位置 32×32 里真的
  有像素变回去（实测 144 px），这样"收到了形状"和"真的画上了"不会被混为一谈。
  已知代价：桌面复制只复制主输出，多显示器副屏不进画面（GDI 通路摄整个虚拟桌面），
  所以副屏共享仍需显式 `ESS_CAPTURE=gdi`。

- **实测延迟**（localhost、白闪注入 → 浏览器呈现，`scripts/latency-probe.mjs`）。
  主指标来自**真机 1920×1080 桌面采集**：全屏白闪窗口作源，`ESS_MOTION_HOLD=600`
  把画面停在视频平面，观看窗口放在屏幕角落里保持可见。一键复现：
  `scripts/latency-run.sh --fps 60 --maxw 1920 --maxh 1080 --bitrate 6000000`
  （脚本会自己起服务器/观看页/白闪源/Edge 窗口，并在 `vis != visible` 时判结果无效）。

  | 画面通道 | 发送端 | 呈现帧率 | 丢帧 | 延迟 min / 中位 |
  |---|---|---|---|---|
  | 视频轨 H264，1280x720@30（旧默认档） | 30 fps | 30.0 fps | 0.5% | 76 / 76 ms |
  | **产品默认档：1920x1080@30，5.6 Mbps（自动）** | 30 fps | 30.0 fps | 2.6% | 84 / 91 ms |
  | **产品默认档：1920x1080@60，11.2 Mbps（自动，DXGI 采集）** | **61 fps** | **59.7 fps** | **2.6%** | **75 / 81 ms** |
  | 1920x1080@30，6 Mbps（2026-10-31 复测，GDI 采集，平衡档） | 30 fps | 30 fps（599 帧） | 2.2%（17/782） | **105 / 113 ms**（max 119） |

  复测这一行比 2026-10-28 的 1080p30 基线整体高了约 30 ms，**没有归因到本轮改动**：
  同一份日志里送入尺寸控制器一次都没动过（无「视频平面送入尺寸」行）、编码器全程
  1920x1080、丢帧率与基线一致（2.2% vs 2.6%），也就是队列/编码侧的行为没变，差的
  是一整段平移。可疑的是机器状态（当天连续跑了十几轮会话与两次 release 构建）。
  这一项**记为待复现**，不当成已解释。

  默认档现在是「跟随屏幕分辨率 + 按 帧率x像素 自动定码率」。从 720p 换到 1080p
  要多付约 15 ms（呈现解码更重），所以这变成了一个**用户可选**的档位，而不是代码里
  写死的默认：分享端「高级：画质」里有清晰度上限与码率两个下拉。
  | 图块（无损，`ESS_VIDEO=0`） | 30 fps | 观看端 21 fps | — | 29 ms（数据通路首次变化） |

  合成屏 1280×720 的编码档位对照（同一测量台，用于选档）：

  | 编码档位 | 呈现帧率 | 丢帧 | 延迟 min / 中位 |
  |---|---|---|---|
  | VP8 + screencast（旧默认） | 6 fps | 22% | 128 / 157 ms |
  | VP8 − screencast | 25 fps | 4% | 114 / 133 ms |
  | H264 + screencast | 26 fps | 0.4% | 55 / 74 ms |
  | H264 − screencast | 26 fps | 2% | 104 / 105 ms |

  白闪是"整屏剧变"的最坏情况，且含 0–33 ms 采集量化、源窗口定时器最多 16 ms 量化；
  视频轨那个 76 ms 还包含进出平面的两次交接。测量要求观看窗口真的可见（被遮挡时
  Chrome 停止呈现，`requestVideoFrameCallback` 不再触发），数据通路可用
  `--mode canvas` 在后台标签页测。`--bright` 调判白阈值（观看窗口自己也在画面里，
  全屏闪白时它占的像素达不到 80%，用 0.55）。
- **鼠标光标已进画面**：GDI `BitBlt` 按设计不包含硬件光标，观看端本来完全看不到
  指针。采集层现在用 `GetCursorInfo` + `GetIconInfo`（热点）+ `DrawIconEx` 把光标
  画进位图（`ESS_CURSOR=0` 关；Windows 报 `CURSOR_SUPPRESSED`——触控输入后指针被
  抑制——时同样不画）。验收用 `WindowsCapture::cursor_footprint()`：BitBlt 一次 →
  快照 → 画光标 → 再快照，只断言这一步改了哪些像素，所以桌面自己在动也不会污染
  结果；实测 144 px、12×19、正好落在测试停放的屏幕中心。
  （跑法：`cargo test -p ess-capture --release -- --ignored --nocapture`。）
- **链路自适应闭环（§9 守门员已接上真实信号）**：会话每 250 ms 调一次
  `Room::get_stats()`（libwebrtc 原始统计），取视频轨的 `outbound-rtp`（目标码率、
  实际编码分辨率/帧率、每帧编码耗时、平均 QP、平均发包排队延迟、
  `qualityLimitationReason`）、`transport`/`candidate-pair`（GCC 估计的可用上行、RTT）
  与 `remote-inbound-rtp`（观看端回报告的丢包与 RTT），喂给 `ess-core::governor`。
  累计计数器一律取**区间增量**，实发速率走 α=0.3 的指数平均；开局 3 s 预热，
  且刚发过整帧后的 2 s 内不做决策（那 1.2 MB 是我们自己堵进通道的，不是链路差）。
  实测（`ESS_PERF=1` 打 `STATS` 行，`ESS_STATS_DUMP=1` 打原始条目直方图）：
  | 场景 | GCC 估计 | 实发 | 编码器 | 受限原因 | 守门员动作 |
  |---|---|---|---|---|---|
  | 空闲桌面 1080p30 + 1 观看端 | 5.6–6.1 Mbps | 0.9–2.1 Mbps | 1920x1080@2 | none | 无（保持 30 fps） |
  | 全屏持续重绘 1080p60 | 5.3 Mbps | 0.8–2.3 Mbps | 1920x1080@57–60 | none | 无 |
  | 码率上限压到 300 kbps + 持续重绘 | 0.63 Mbps | 0.15 Mbps | **480x268@59–60** | **bandwidth** | 无（帧率是承诺，编码器自己降分辨率） |
  | E2E（合成屏 1280x720@10） | — | — | — | 排队 140 ms | 「链路收紧 → 图块预算 1018 kbps，帧率保持 10 fps」 |
  执行器按判据**分流**，两路都接上了：
  - **算力受限**（`encode_ms > 预算x0.9` 或 `cpu_limited`）→ 动采集帧率。阶梯按用户
    上限等比缩放（Text 阶梯 15/10/5/2 配 30 fps 上限＝30/20/10/4），降完还能回到用户要的那档。
  - **带宽/排队受限** → 给图块通路设每秒预算
    `tile_budget = (可用上行 − 视频轨目标码率) x 0.6`，下限 200 kbps；预算装不下当前
    无损需求时（要求一秒至少塞得下两次这种量，避免在边界上抖），画面交给媒体通道出，
    且**预算没松开就不退回来**——每次退出都要补一次差分修复，而那正是链路装不下的东西。
    退回无损时走的是既有的"先修复后 off"契约，观看端画布仍然逐字节正确。
    没有拥塞证据时预算为 0（不限制）。
  离线契约测试：`crates/ess-core/tests/budget.rs`（紧预算 → 逼进平面 → 预算解除 →
  修复先于 off；反向对照：没有预算时同样的画面序列一次都不切平面）。
  在线核对（`ESS_PERF=1` 的 `STATS` 行带 `tile_budget=` / `forced_plane=`）：日常演示
  （合成屏 1280x720@10）预算算出 1.3–1.6 Mbps，而图块实际需求只有 0.09 Mbps，所以
  `forced_plane=0`——不触发是对的。
- **预算逼进媒体平面的真机样本（`scripts/forced-plane.sh`）**：localhost 上没有差网络，
  但预算不是猜的——把视频轨目标码率压到 300 kbps 并让画面持续重绘，H264 自己报
  `bandwidth`，于是 `tile_budget = (可用上行 − 视频轨目标) x 0.6` 真的落到窄档；再叠一条
  `ESS_MOTION=0` 关掉「大面积运动 → 切视频」的策略判定，**平面切换就只能由预算引起**。
  合成屏 1280x720@30、动画 8 s 后静止，实测：

  | 阶段 | 图块预算 | forced_plane | 采集上限 | 编码器实际输出 | 切换计数 |
  |---|---|---|---|---|---|
  | 静止前（动画中） | 858–939 kbps | 1（已进平面） | 30 | 320x180@18→3 | 1 |
  | 静止后 | 169–213 kbps | 1 | 30 | 320x180@0–2 | **2（退回无损）** |

  四条断言全过：执行器真的动过（不触发就直接 FAIL）、**帧率全程没被动过**（带宽受限
  不该拿帧率出气）、静止后退回无损、且退回后观看端画布**逐字节等于期望终帧**
  （先修复再 off 的契约在真实窄预算下仍然成立）。
  这一跑还抓出一个真缺陷：**退出判据原来用「被逼进来那一次的每秒需求」，而那个数在
  平面期内再也不更新**——动画停了、画面静止，平面却再也下不来，观看端看到的是永久糊掉
  的小字（主流远控的行为是"停下来就变清晰"）。现在按**当前**变化量折算需求
  （平面期内仍逐帧比对块级差异，只是不编码），新变化掉进预算就退；离线用
  `settled_picture_returns_to_lossless_even_while_budget_stays_tight` 钉住，并且做过变异
  检查：把判据换回旧写法后只有这一条测试 FAIL，说明它真的能抓住这个缺陷。
  踩过的坑：`availableOutgoingBitrate` 在本机只是跟着视频目标码率爬（数据通道不走
  pacer），直接拿它和实发比会误判拥塞（实测连降两档到 5 fps）；现在这条判据只在有
  真实拥塞证据（排队 >50 ms / 丢包 >1% / 编码器报 bandwidth）时才生效。

  webview 窗口调 `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`（Win10
  2004+），人眼看着正常，采集 API 里等于不存在；`ESS_HIDE_SELF=0` 可关掉（调试用）。
  实测证明分三层，且都带反向对照：
  | 用例 | 采样点 | GDI BitBlt | DXGI 桌面复制 |
  |---|---|---|---|
  | 普通窗口压在酸橙底屏上 | 窗口内一点 | `(255,0,255)` 采到 | `(255,0,255)` 采到 |
  | 同窗口设 `WDA_EXCLUDEFROMCAPTURE` | 同一点 | `(39,39,39)` 采不到 | `(39,39,39)` 采不到 |
  | 排除窗压在**可采集**酸橙窗上 | 同一点 | `(0,255,0)`＝露出后面的画面 | 同左 |
  第三行是关键：排除是「透明」而不是在画面上挖一块黑洞，所以控制窗飘在任何内容上
  都不会留残影。跑法 `ESS_PX=x,y cargo test -p ess-capture -- --ignored --nocapture`
  的 `probe::dump_pixel` / `duplication_dump_pixel`（多点用 `ESS_PX="x,y;x,y"`）。
  端到端也复核过：全屏酸橙底 + 真机 1920×1080 会话，观看端 `--dump` 的帧里
  非底色像素 **742,892（35.8%）→ 92,508（4.5%）**，剩下的 9.2 万是光标和任务栏
  （任务栏本来就属于桌面，主流远控同样会采到）；控制窗整块消失。
  这里的顺序有坑：先起分享端再起底屏，控制窗会被底屏压住，两次采样都会"干净"，
  测不出任何差异——第一次跑就是这么假绿的。必须先证明测量能看见泄漏。

## 浏览器观看（免安装客户端）

```bash

# 上游 livekit-client@2.23.0 的 UMD 按脚本内钉的 sha256 取回，两者都不入库）
scripts/build-web.sh

# 一条命令就绪全部三步（服务端 + 观看页 + 共享端都在里面）
target/release/ess-share --host-viewer --room demo

# 或者手工分开：
# 终端 1：LiveKit
"$LIVEKIT_SERVER" --dev

# 终端 2：观看页（静态文件 + /token；与 --host-viewer 用的是同一份实现）
target/release/ess-serve --url ws://127.0.0.1:7880 --room demo

# 终端 3：共享端

# 浏览器打开 http://127.0.0.1:8088/
```

一键：`scripts/demo-browser.sh`（合成屏）或 `scripts/demo-browser.sh --real`（主屏）。

- 浏览器里是**同一份接收管线**（WASM）：版本判定、滚动组原子应用、整帧分片
  重组都在 Rust 侧；JS 只做 LiveKit 连接、BGRA→RGBA 拷贝画布、500 ms 状态报告。
- 迟到加入的观看方：发送端在 `ParticipantConnected` 时强制重发整帧（§6.3.1）；
  观看方报告 `layout_id=0`（尚未收到整帧）时也会兜底重发——整帧若在其数据
  通道就绪前发出而丢失，能自动恢复。
- 观看端自己断线：JS SDK 会自动重连。页面在 `Reconnecting` 只提示不断流，
  `Reconnected` 必须把内部 `connected` 恢复——它一旦停在 false，500 ms 上行报告就
  永久不再发送，发送端再也补不回断线期间丢掉的块，画面会冻在断线前那一刻。
  重连后若视频轨是一条全新的 `Track`，会重新走"等第一帧真画面才接管"的门，
  避免 `<video>` 还没出画就盖住画布闪一下黑屏。
- 局域网观看：图形分享端或 `ess-share --host-viewer` 已经把这三步做完（服务端 `--bind 0.0.0.0`、
  观看页 `--bind 0.0.0.0`、探测本机地址）；手工路径是 `ess-serve --bind 0.0.0.0
  --url ws://<本机IP>:7880` 配 `livekit-server --dev --bind 0.0.0.0`。
  探测把 VPN/代理网卡排在真网卡之后（**同网段网关**才算真 LAN），日志列出全部候选。
  生产环境用 TLS（`https`/`wss`），否则浏览器会拦截混合内容。
- **图块平面下按需订阅视频轨（2026-11-06）**：`plane=tiles` 连续 10 s 就
  `setSubscribed(false)` 把视频轨摘掉，进入视频平面时再挂回来。发送端在图块平面下仍会按
  ~2 fps 喂保活帧（让切换时画面是当前的），而浏览器没有原生观看端那道 `VideoMode` 闸门，
  那些帧会被真的收下来解码再丢掉——手机上等于白烧解码器（实测图块平面下
  `inbound-rtp video` 仍有 1440x808@2fps）。迟滞 10 s 是为了让滚动/翻页这类短暂进出
  不来回摘订阅，代价只有复订时的一次关键帧。同一时刻发送端也停喂了保活帧
  （`ESS_IDLE_STOP`，默认 10 s），两端各自省下的是自己那一半。
- 页面 HUD 显示连接状态、画面尺寸、FPS、声音状态、收到的消息数；第二行是**传输速率**：
  `下行 3.24 Mbps（图块 2.10 · 媒体 1.14）  上行 26 kbps`。口径是链路上真实的字节流速，
  不是有效载荷——数据通道按**到达**字节计（被本机新鲜度闸门丢掉的也算，它一样占了带宽），
  媒体按 `getStats` 的 `inbound-rtp.bytesReceived` 差分（视频 + 音频）。两路分开报是因为
  图块与媒体是两条互斥的出路，一眼能看出"现在贵在画面还是贵在媒体"。像素在浏览器
  内与原生观看端一致（验收：对最终帧做 FNV 哈希比对）。系统声音挂在这一页自己的
  `<audio>` 上，见「系统声音」一节。技术计数默认收起，顶栏「详情」（或按 `D`）才显示。
- **桌面观看界面（2026-11-05，桌面优先）**：
  - 顶栏：连接状态 / 分辨率 · 帧率 · 平面 / 缩放读数 / `1:1`（或「适应」）/ 声音 /
    详情 / 全屏。3 秒无操作自动淡出，移动鼠标或点一下画面唤出。
  - 鼠标滚轮以光标为锚缩放（1× 适应 ~ 8×）；放大后左键拖动平移；
    双击或按 `1` 在「适应 / 100%」之间切换；按 `0` 回适应。
  - 键盘：`F` 全屏、`0` 适应、`1` 1:1、`+`/`-` 缩放、`S` 声音、`D` 详情、`R` 刷新。
  - 首屏状态：正在连接（令牌）→ 已连接等待画面（分享端还没开始）→ live；
    断线时保留最后一帧并在顶部提示「正在重连」，永久断开才落错误页 + 重新加载。
  - 声音默认静音（同机外放会回声），有音频轨时提示一次；**开发期每次加载都从静音
    开始**（不恢复上次的“开”，否则刷新后自动外放会形成环回），要听就点一次「声音」。
  - 手机仍可用同一套手势（单指拖动 / 双指捏合），但不作为这一轮的主路径。

## 系统声音（WASAPI 环回）

「共享电脑声音」抓的是**默认输出端点的混音**，不挑应用、不装虚拟声卡——和 RustDesk /
UU 远程同一件事，但这两家在 Linux/Windows 上普遍要靠虚拟声卡才出得来，这里直接用
WASAPI render loopback。

链路：`ess-audio`（COM 线程 + 环回，10 ms 一块的交织 s16）→ `NativeAudioSource` →
音频轨 `ess-audio`（`TrackSource::ScreenshareAudio`）→ LiveKit → 观看端。

- **必须补静音**：输出设备安静时 loopback 一个包都不给，不补的话下游时间轴会断，
  听感是变速/卡顿。所以每 10 ms 一定交一块，哪怕全零。
- **float→s16 要饱和**：环回拿到的是总线混音，应用推满音量时真会给到 |x|>1.0，
  不夹就溢出绕回成大爆音（`ess-audio` 单测里那条就是防这个）。
- AEC/降噪/AGC 全关：进来的已经是混音结果，再挂语音处理会把音乐和音效糊掉。

### 带宽实测（`scripts/audio-dtx.sh`，48 kHz 立体声，一个观看端）

| 状态 | DTX | 线路上行 | 编码器目标 | 发包 |
| --- | --- | --- | --- | --- |
| 静音 | 关 | 4.5 kbps | 64000 | 53 pkt/s |
| 静音 | **开（默认）** | **0.2 kbps** | 64000 | 7 pkt/s |
| 440 Hz 音调 | 关 | 132.4 kbps | 64000 | 50 pkt/s |
| 440 Hz 音调 | 开（默认） | 131.1 kbps | 64000 | 50 pkt/s |

线路开销正好是目标码率的**两倍**，因为 `red:true`（默认）在每个包里带上一帧的冗余副本，
丢一个包也不掉字。按比例缩放实测：请求 32/64/128 kbps → 线路 66.6 / 130.4 / 264.0 kbps。
这 131 kbps 只走**一次**上行、与观看人数无关（见扇出验收），所以留着冗余比省那一半划算。

量带宽只能用发送端 `audio` outbound-rtp 的字节增量。**不要**用观看端的块数：接收端
音频 sink 空了也照样按 10 ms 交静音帧（静音 DTX 生效时它仍报 99–197 块/s），那个数
只证明"这一路订阅上了"，不证明线路上花了多少。

### 端到端验收（`scripts/audio-e2e.sh`）

本机播放 440 Hz 正弦 → 分享端环回 → 音频轨 → 观看端把收到的 PCM 落盘成 WAV →
`scripts/audio-analyze.mjs` 做 Goertzel 频点分析。两格，顺序不能反：

| 用例 | 观看端到达率 | 收到的内容 |
| --- | --- | --- |
| `--no-audio`（负对照） | 0 块/s | 0 样本，rms 0，g(440)=0 |
| 默认共享 | 98.8 块/s | rms 0.353、g(440)=0.32、g(1000)=0.0000（比值 6864） |

负对照先跑：没有它，"收到 N 块"可能只是统计口径自己算了个东西。音调源的理论值是
rms 0.354 / g(440)=0.4994（幅值 0.5 的正弦），穿过 Opus + 网络之后能量基本没掉，
对照频点上归零——这证明到达的是那个音，不是"有点响声"。

### 观看端行为

- **浏览器**：独立 `<audio>`（`<video>` 是 muted 的，不能共用）。**默认静音且不播放**
  （元素保持 `paused`），点顶栏「声音：关/开」（文案是**当前状态**，不是点击动作）
  才真正 `play()`；切换时给一句 toast 反馈。开发期每次加载都从
  静音开始，不恢复上次的开启状态，避免同机测试时外放被环回再抓一遍。注意 LiveKit 的
  `track.attach()` 会按“有没有音频轨”重写 `element.muted`（音频轨就是 `false`），
  所以静音必须在 attach **之后**再设一次。浏览器的自动播放策略可能先拦一下，任意一次
  点击/按键都会顺手 `room.startAudio()` 放行（不做遮罩，对只想看画面的人是打扰）。
  HUD 多一项 `声音:开/关/无`。
- **原生 `ess-view`**：**故意不接扬声器**。分享端和观看端同机时，这里放出来的声音会被
  环回再次抓走、再推给所有观看端，形成回声环。要验内容用 `--audio-dump out.wav`，
  要调声道用 `--audio-channels`（必须与发布端混音格式一致，否则交织错位成刺耳噪声）。
- **同机自测的通用注意**：只要观看端真的外放，就会被分享端的环回抓到。要么静音观看端，
  要么用 `--no-audio`。

开关：UI 复选框「分享系统声音」（默认开）、CLI/UI 的 `--no-audio`、环境变量
`ESS_AUDIO_DTX=0`（关静音抑制，做 A/B 用）、`ESS_AUDIO_BITRATE=<bps>`（改档位）。
混音格式（采样率/声道数）与档位、DTX 状态都写进日志一行，出问题时无需再猜。

同一段全屏滚动内容，无损图块平面是 30 fps + SSIM 1.0（实测 1,194 kbps），媒体通道同一素材
稳态也能 30 fps 但 SSIM 只有 0.74（那份码率只够 960x540@30——现在由 `entry_scale` 在平面
关着的时候就定到那个尺寸，不在切换那一帧改），所以链路够用
时**不该切平面**——这条判据已进 `ess-core`（wide/narrow 一对测试锁住）。**两种内容都验过**：
纯滚动（`ESS_DEMO_BLOCK=0`）下平面一次都没开、8 秒 30 fps 全程由滚动宣告扛住、观看端终帧
逐字节一致；默认 demo 在滚动页上还叠了一块独立移动的红块，那不是平移，滚动检测判 None，
切平面才是对的（估算需求 12.07 Mbps > 链路 5.90 Mbps）。脚本按内容模式分别断言，两种都跑通。
见 IMPLEMENTATION.md 的 O-22 / O-23。

**「画质·流畅度」是三档真开关**（2026-10-31，`scripts/product-mode.sh` 14/14 PASS）：

```bash
scripts/product-mode.sh # 三档各自的合同与代价：宽链路一遍、饿码率一遍、切换沿一遍，互为反向对照
```

| 档 | 承诺 | 花掉的代价 | 实测（1280x720 合成屏、最坏运动内容、本机 ~5.9 Mbps） |
|---|---|---|---|
| `smooth` 流畅优先 | 帧率合同优先：码率按 **0.15 bpp** 给（上限 16 Mbps），大面积运动**一律**走媒体通道；交付不足 1 s 证据就缩送入尺寸（下限 0.25，平面进入后头 2 s 的爬坡不动手） | 带宽；饿码率时是像素 | 自动 4.15 Mbps：编码器 **1280x720@30**、带宽受限 0%、稳态交付 **29.4–30.2 fps**、**SSIM 0.9414 / PSNR 28.5**；强制 300 kbps：缩到 **320x180**，交付仍有 **29.6–30.2 fps** |
| `balanced` 平衡（默认） | 链路装得下就留在无损；进平面后按 2 s 证据缩尺寸（下限 0.4），码率 0.09 bpp。0.09 bpp 买不起原尺寸满帧率，所以送入由 `entry_scale` 在**开场与平面退出时**就定到 0.75（切换那一帧不改尺寸） | 分辨率（画面被压小后再放大显示） | 自动 2.49 Mbps：切换沿那一遍编码器 **960x540@30、带宽受限 0%**、交付 29.8–30 fps、**SSIM 0.7416 / PSNR 18.3**；冷启动那一遍里编码器还会再降到 640x360（这份内容 0.09 bpp 确实不够） |
| `clear` 清晰优先 | 保分辨率：编码器 `MaintainResolution`，我们**不**主动缩送入尺寸 | 帧率 | 强制 300 kbps：死守 **1280x720**，交付只剩 **0.2–0.4 fps**（画质侧未单测：宽链路上这一档多半根本不进平面） |

**那两行 SSIM 才是档位的说明书**：同一素材同一条链路，流畅优先比平衡多要 1.66 Mbps，
把交付画质从 0.74 抬到 **0.94**（内容匹配中位 MSE 155.7 → 10.9），因为编码器不再需要
把画面压到 540p 再放大显示。旧记录里"码率过了 ~1.5 Mbps 就没处花、各档 SSIM 分不开"
是**错的一般化**——那是 0.09 bpp 这一侧的事实（一旦降过尺寸就钉在 540p30 回不来）；
跨过 0.15 bpp 这个点，尺寸压根不用降。无损图块平面仍是 1.0，所以三档的真实排法是
「无损 1.0」→「流畅优先 0.94」→「平衡 0.74」，前两条之间是"糊与不糊"。
数据来自 `MODES="balanced smooth" TIERS=0 bash scripts/video-plane-quality.sh`
（落盘量画质那一遍，所以它的 fps 列按落盘代价读）。
从界面这条路也单独验过一次：`ess-share-ui --autostart --demo --fps 30 --mode smooth`
观看端解出 **1280x720**，同一台换 `--mode balanced` 解出 **960x540**——档位确实穿过
表单进了会话，不是只在 CLI 里生效。

入口：CLI `ess-share --mode clear|balanced|smooth`、环境变量 `ESS_MODE`、Tauri 表单
「画质·流畅度」下拉（`--autostart` 会回填）。档位在编码器上真的分得开——30 fps 设定下
流畅优先多要的 1.66 Mbps 换来 720p 原尺寸与零带宽受限；把降级偏好或控制器阈值调反，
脚本的阶段 B 两条断言立刻挂。

**合同是"按你设定的帧率兑现"，两档设定都验过**（`FPS=30` 与 `FPS=60` 各跑一遍，均 6/6
PASS）：60 fps 设定时流畅优先要 8.29 Mbps、平衡档要 4.98 Mbps，两档都交付
**59–60.4 fps**、编码器全程 1280x720@60、`nack=0`。这时流畅优先**没有**换来可见差别，
脚本据此判它在这一条链路上是「保险档」：只多花带宽，换的是"链路一落就有余量"，
而不是更好的当前画面（饿到 300 kbps 时它照样把尺寸缩到 320x180 守住 59.8 fps，
清晰优先同一条只有 0.2 fps）。这条判据本身就是反向对照——如果哪天平衡档在 60 fps
下开始报带宽受限而流畅优先不解除，那才是档位坏了。

**量帧率与量画质必须分两遍跑**（同一轮的更正）：`--video-seq` 让观看端每帧落一张 2 MB PPM
（30 fps 就是 60 MB/s），而 `NativeVideoStream` 的 sink 队列容量只有 1，写盘一慢帧就在队列
里被丢掉。所以 `video-plane-quality.sh` 表里的**交付帧率列是落盘代价下的读数**（此前据此
记的"自动档 18–19 fps、离合同差 35%"作废），SSIM/PSNR 仍然有效（按内容配对，与写盘速度无关）。
帧率看 `product-mode.sh`（不落盘、只数帧，取第 2–4 个 5 s 窗口的最差值当稳态；第 1 个窗口
是平面进入 + 码控爬升，13–20 fps，不算稳态）。

**切换沿自己是一条合同，不是稳态的边角**（#41，2026-10-31）。上面那种"一开场就动"的时序
测的是会话冷启动；用户真正遇到的是**画面静止若干秒后突然滚动**。所以合成屏多了
`ESS_DEMO_ANIM_DELAY`（先静止 N 帧），验收脚本多了阶段 C，观看端多了 `ESS_GAP_TRACE=1`
（逐条打印 ≥120 ms 的画面间隔）。量出来的口径写在脚本的 `gap_pass` 一处：
**最坏有流窗口 p95 ≤ 2.5×设定周期 + 2 ms、max ≤ 4×周期 + 4 ms**，另外阶段 C 不容任何
≥120 ms 的空洞。现测（30 fps，重复三轮）：进入平面后第 1 秒 15.2–15.8 fps（编码器起步，
两档一样，第 2 秒起就满帧率），最坏窗口 p95=67 ms / max=68–73 ms，**没有一条 ≥120 ms 的
空洞**；修之前是 263–422 ms。根因不是爬坡本身，而是我们把"改送入尺寸"办在切换那一帧上——
尺寸一变编码器要重配并补关键帧，那笔钱正好落在用户看得见的一秒里；现在尺寸在开场与平面
退出时预置（平面关着时观看端根本不收视频帧），代价 invisible。60 fps 两档 14/14 PASS，
但抓到一次孤立的 101 ms 空洞（那一秒发送端自己只 `vsent=52.9`，`ql_bw=0`、`qdelay=0`、
`nack=0`），归到延迟/卡顿归因线（任务 #42）继续查。

自检：**解出帧数 ÷ 送入帧数 必须 ≤ 1**，超过说明房间里挂着第二个发送端（上一轮没停干净），
该行数据作废。详见 `IMPLEMENTATION.md` §14.4 结论 4 与 O-22。

**当前实测结论（2026-10-29）**：800 kbps→5 Mbps 的交付 SSIM 一直趴在 0.66，加码率买到的
是帧率不是画质；而帧率仍然守不住 30 fps 的合同（观看端解出 5.5–13.6 fps，内容进度约真机
的 72%）。数字与根因分析见 `IMPLEMENTATION.md` §14.4 结论 4 与未决项 **O-22**。

带宽执行器的真机验收（细节与实测表在「链路自适应闭环」一节）：把视频轨压到 300 kbps
并持续重绘，逼出真实的窄图块预算；`ESS_MOTION=0` 关掉策略切换，于是平面只能由预算来动。
四条断言：进过平面、**帧率没被动过**、静止后退回无损、终帧逐字节一致。

断线重连两阶段验收，都要求通过：

- **阶段 1（2 s 中断后恢复）**：跑到中途杀掉服务器、2 s 后原端口重启。发送端日志
  必须出现 `与服务器的连接中断，正在重连…` → `视频轨已随重连自动恢复` →
  `重连成功：补发整帧重建观看端画面`，且恢复后观看端画布仍然**逐字节等于期望终帧**
  （实测 `fulls` 从 2 变 3，画布 2 764 816 字节一致）。SDK 在全量重连里会重新发布
  本地轨并保留同一个 `Track`/`NativeVideoSource`，所以视频平面不需要重建。
- **阶段 2（永久中断，要求有界失败）**：杀掉服务器且不再重启。SDK 只会停在
  `Reconnecting`（实测 60 s 内不报 `Disconnected`），会话会永远挂在"正在共享"上，
  观看端画面冻在旧帧。会话主循环因此每秒轮询 `connection_state()`，超过
  `ESS_RECONNECT_GRACE_S`（默认 30 s，最小 5 s）没恢复就以错误结束，UI 落到
  `error` 态并给出原因。实测 grace=8 时 8 s 内退出。

脚本每次杀完进程都会确认 7880 不再监听——之前有一次用 `taskkill` 打算杀服务器却
打偏了，"断线"根本没发生，整轮结论都是假的。

扇出验收：一份上传喂 N 个观看端。这是本项目立项的第一约束（服务器上行带宽），
也是 1:1 直连的远控做不到的那一条。实测（合成屏 1280x720@10，20 s）：

| 观看数 | 全程数据通道 | 稳态数据通道 | 发送端编码耗时/秒 | 画布=期望终帧 | 各端互相一致 |
|---|---|---|---|---|---|
| 1 | 145 kbps | **0** | 78 ms | PASS | 一致 |
| 4 | 109 kbps | **0** | 81 ms | PASS | 一致 |
| 12 | 203 kbps | **0** | 83 ms | PASS | 一致 |
| 12（全程动画，视频轨） | 108 kbps | **0** | 69 ms | 见下注 | 一致 |

- **稳态为 0**：画面静止、所有人都追平之后，发送端一秒不再发一个字节——与人数无关。
  全程那一列随人数涨（145→203 kbps）全部来自**每个观看端加入那一次**的整帧与补齐，
  约 25 KB/端，是一次性成本不是持续成本。
- **编码耗时 78–83 ms/s 不随人数变化**：编一次、发一次，扇出是服务器的事。
- 两点测量边界：`稳态/全程` 两列只统计**数据通道**（图块通路）的字节，视频轨的码率
  要看 `ESS_PERF=1` 的 `STATS` 行（`target=` / `egress=`）；`画布=期望终帧` 这一列只在
  动画已经停下时成立，`ESS_DEMO_ANIM` 拉长动画后终帧本来就不是 `ess-gen-expected` 生成的
  那张图，此时看**各端互相一致**（12 端逐字节相同）。

## 已知边界（与文档一致）

- 整帧（布局变更/首次）走可靠通道分片（≤16 KB/片），分片期间可靠大块会
  队头阻塞 lossy 小消息（O-2 实测 p95 2→28 ms）——只发生在首帧/改分辨率时。
- 采集双通路：GDI `BitBlt`（≤50 fps 默认）与 DXGI 桌面复制（`fps>50` 自动切，
  `ESS_CAPTURE=gdi|dxgi` 覆盖）。复制通路只复制**主输出**，副屏不进画面；GDI 通路
  现在按虚拟桌面（`SM_*VIRTUALSCREEN`）取尺寸与原点，多屏内容能整体进画面。
  真正的按显示器选择/按窗口采集仍待 WGC（`ScreenSource` 接口不变）。
- 修复路径：NACK 未接（LiveKit 不暴露丢包回调），依赖 500 ms 状态报告兜底；
  §6.6 修复预算在模型里已验证，传输层尚未接入（O-12 剩余项）。
- 守门员两路执行器都接上了（算力→采集帧率，带宽→图块预算），带宽那一路也有真机样本了
  （`scripts/forced-plane.sh`，见「预算逼进媒体平面的真机样本」）。仍然没做的是**真实
  差网络**：本机 GCC 估计会一路爬上去，这里的窄管子是用「把视频轨目标码率压到 300 kbps
  并持续重绘」逼出来的——预算、进平面、退平面、退回无损后的逐字节一致都是真的，
  但"公网丢包 + RTT 抖动"下的行为仍需在限速网络或第二台机器上补测（O 项）。
